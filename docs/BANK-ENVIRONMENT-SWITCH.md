# Смена тестовой среды банков на боевую без обновления приложения

Код приложения общий. BCC/ВТБ, среда, доступные страны/валюты, тарифы и ссылка платёжной формы выбираются сервером. В приложении уже разрешены известные официальные sandbox/live адреса BCC и ВТБ, в том числе переходы3DS. Возврат ведёт на защищённый HTTPS маршрут JOBA; после возврата сервер независимо проверяет платёж. Статус клиента не активирует покупку.

Предпочтительное распределение: Казахстан/Кыргызстан — BCC, Россия/Беларусь — ВТБ. Банк должен подтвердить разрешённые валюты/страны конкретного мерчанта. Нельзя включать KGS/RUB/BYN по предположению или пересчитывать курс самостоятельно. Когда основной банк страны не подключён, существующая серверная совместимость может использовать другой настроенный банк; это не подтверждение банковского соглашения.

## Когда банк выдаст боевые параметры

1. Завершить обязательные sandbox-кейсы и согласовать callback с банком. BCC сейчас имеет незакрытые реальные банковские кейсы: тестовые картыRC51, возврат после клиринга и регистрация уведомлений. Наличие этой инструкции не означает допуск к live.
2. Владелец может прочитать GET `/api/v1/admin/billing-runtime` в своей админской сессии: среда/страны/валюты и количество незавершённых платежей, без секретов. Сверить и завершить прежние pending-платежи ДО переключения. Старые записи не переименовывать в production; для спорного платежа сохранить прежнюю конфигурацию и выполнить сверку по регламенту банка.
3. Сохранить защищённую резервную копию только меняемого банковского файла; не изменять другие интеграции. BCC файл: `/etc/joba/payments/bcc.json`; ВТБ: `/etc/joba/payments/vtb.json`. В контейнере они доступны как приватные read-only настройки. Права600, владелец1000:1000. Подготовленный атомарный BCC-only backup/rollback helper и проверки лежат в отдельной ветке банковского аудита; не подменять их ручной перезаписью всего каталога настроек.
4. Установить выданные конкретному проекту идентификаторы/пароли/ключMAC и `environment:"production"` для нужного банка. BCC получает промышленныйTID и две компоненты ключа, формирует ключXOR локально в защищённой среде. Компоненты нельзя отправлять сторонним XOR-сайтам. Не переносить публичные тестовые значения, реквизиты другого проекта и секреты в клиент/репозиторий/отчёт.
5. Перезапустить API с прежней базой и файлами. Это серверная операция; APK/AAB/IPA пересобирать для смены среды и реквизитов не требуется. Снова проверить защищённый runtime endpoint, предложения тарифов/валют, форму банка и callback. Не менять параметры действующей интеграции без отдельной авторизации владельца.
6. Реальный live-платёж/возврат — только после согласования точного сценария и суммы. Минимальные суммы и возможности определяет банк. При ошибке вернуть только конфигурацию изменённого банка из резервной копии, перезапустить API и проверить остальные интеграции. Не откатывать/удалять платёжные записи и не повторять спорное списание/возврат вслепую.

## Проверки

`npm run build --workspace @marketplace/api`

`node --test services/api/test/bank-environment-switch.test.cjs`

`bash scripts/flutter-mobile.sh test test/bank_environment_switch_test.dart`

Проверки используют имитацию банка и временную базу; mode production в тесте не означает реальный live-запрос. Они подтверждают совместимость текущего клиента с серверным переключением. Если банк изменит сам протокол, выдаст другой неразрешённый домен или потребует новыйSDK, потребуется отдельная оценка совместимости; обещания об отсутствии любых будущих обновлений здесь нет.
