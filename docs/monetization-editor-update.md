# Блок 5: редактирование монетизации

Форма A16 сохранила отдельные переключатели баннеров и рекламного доступа. Добавлены открытие сохранённой версии в форме, редактирование своего черновика с expected_version и создание копии чужой/опубликованной версии. Курсорная ссылка позволяет открыть следующую страницу списка версий. Провайдер, сохранённый в версии, не теряется из select, если подключение пока отсутствует.

GET/PATCH `/admin/monetization-configs/{id}` требуют billing и MFA, ограничены страной сотрудника. PATCH доступен автору только в draft, фиксирует причину и аудит. Публикация требует другого сотрудника; проверка версии теперь обязательна и для validate. Несохранённое редактирование блокирует команды версий. На время сохранения блокируются поля и кнопки; ошибка сохраняет ввод и исходные ограничения доступности контролов.

Добавлены поля дневного лимита рекламных сессий (1–1000) и паузы (0–86400 секунд), по умолчанию 5 и 300. Сервер нормализует флаги, провайдеры, разрешённые inline-размещения, политику награды и лимиты; лишние поля отбрасываются. Награда ограничена возможностями исполнителя: поиск, отклик, публикация профиля. Кредиты не дают чтение поиска. Срок — от минуты до 30 суток; кредиты — 1–100. Ограничения проверяются даже в черновике. Публикация с включённой рекламой дополнительно требует реального провайдера и подтверждений политики.

Настройка едина для страны: публикация заменяет прежнюю действующую конфигурацию независимо от legacy role/platform. Клиент получает опубликованные лимиты и действительное использование, включая оставшиеся сессии и время окончания паузы. Заказчику подписка и предложения подписки не выдаются. Существующие права не удаляются.

Новые тесты API проверяют невалидные настройки, чужой/устаревший черновик, независимую публикацию, применение лимитов в клиентском API, сохранение бесплатности заказчика, замену старой scoped-конфигурации и отказ публикации без рекламного адаптера. Браузерный сценарий проверяет заполнение сохранённой версии, изменение лимитов, блокировку несохранённых команд, PATCH и повторное отображение сохранённых полей. Ранее добавленная потеря ответа создания остаётся в том же сценарии.

Визуальная приёмка A16/A16.preview открыта. Отдельные поля и успешные проверки не означают совпадения всего экрана 1:1. Провайдеры и рабочий сервер этой итерацией не подключаются и не обновляются.

Итог: сборки всех рабочих пространств прошли; полная серия API — 98 passed, 0 failed; браузерный прогон — 72 кадра, без ошибок маршрутов. После добавления транзакционной блокировки публикации по стране повторно прошли сборка API и два связанных сценария. Это не проверка нескольких production-процессов на целевом PostgreSQL.
