# Серверный журнал сбоев приложения

## Как работает

В Android 1.0.3 (5) ошибки Flutter и необработанные Dart-ошибки сохраняются в приватный файл до сетевой отправки. Java/Kotlin uncaught handler записывает тип и стек в отдельный AtomicFile, затем передаёт ошибку штатному обработчику Android/Crashlytics. После перезапуска клиент переносит записи в приватную очередь и только затем подтверждает их получение нативной части. Android 11+ также предоставляет сведения о завершении процесса через ApplicationExitInfo; их отметка получения теперь меняется после сохранения в очереди, а не до неё.

Очередь отправляется сразу, при возвращении приложения и раз в минуту. При отсутствии сети запись остаётся на диске. Один ID повторяется при повторной отправке; сервер не перезаписывает и не дублирует существующую запись. Незавершённая атомарная запись восстанавливается из целого временного файла. Системные завершения подтверждаются от старых к новым, чтобы прерывание переноса не потеряло старые записи. В очереди до 50 отчётов, с приоритетом фатальных; в отдельном нативном файле — до 20. Хранилище находится в sandbox приложения; резервное копирование приложения выключено. При удалении приложения неотправленные отчёты теряются.

Метаданные: версия отправителя, номер сборки, модель/Android, время, экран и до 20 переходов без содержимого полей. Отдельный случайный ID установки не связан с аккаунтом. У системных сведений о предыдущем процессе версия относится к отправителю, а не гарантированно к упавшему APK до обновления. Пароли, токены, URL/контакты редактируются; сервер повторяет редактирование и отбрасывает неизвестные поля. Нативный стек содержит классы и кадры, но не текст исключения с потенциально приватным вводом. Фото, документы, переписка, поля форм и аккаунт не читаются диагностикой.

Приём: `POST /api/v1/public/mobile-crashes`, без сессии, чтобы ошибки до входа тоже доставлялись. Максимум отчёта 24 KiB; ограничение частоты 120 запросов/мин на IP; UUID и допустимые типы/даты проверяются. Сведения клиента не являются доверенным подтверждением события. Flutter framework errors отмечаются как ошибки, а не обязательно закрытие процесса.

Хранение: отдельная таблица PostgreSQL `mobile_crash_reports`, 30 дней, очистка в maintenance. После приёма в обычные server/container logs пишется JSON `event=mobile.crash.received` с ID, типом, версией и экраном. Полный отредактированный стек остаётся в БД. Firebase Crashlytics сохраняется как дополнительный канал.

## Как посмотреть следующий сбой

1. Пользователь после вылета снова открывает приложение и подключается к интернету. Ничего вручную отправлять не нужно.
2. Администратор может читать `GET /api/v1/admin/mobile-crashes?limit=30` с обычной MFA-служебной сессией. Фильтры: `id`, `kind`, `app_version`, `installation_id`. Пользовательские сессии и неавторизованный доступ журнал не открывают. Сотруднику необходимо явное право `GET /admin/mobile-crashes`.
3. Из этой рабочей среды без Firebase Console: `python3 scripts/fetch-mobile-crashes.py --output /tmp/joba-mobile-crashes.json`. Скрипт создаёт одноразовый RSA-ключ, запускает защищённый workflow, получает зашифрованный артефакт и расшифровывает его только локально в файл с правами 0600. Открытые отчёты и стеки не публикуются в GitHub Actions logs/артефактах. Это чтение последних 50 отчётов и агрегатов за неделю по защищённому SSH; пользователей/подписки оно не изменяет.
4. На сервере: `python3 scripts/diagnose-mobile-crashes.py` из текущей ревизии. Для контейнерного журнала искать `mobile.crash.received`. В деталях отчёта `stack` показывает место ошибки, `screen` и `breadcrumbs` — переходы перед ней; системные `reason/status/pss_kb/rss_kb` помогают отличить crash, ANR и нехватку памяти.

Невозможно гарантировать запись при любом физическом выключении, полном отсутствии свободного места или уничтожении процесса до исполнения обработчика. При SIGSEGV/SIGKILL/ANR приложение может не успеть отправить стек: доступные сведения Android 11+ отправляются при следующем запуске. На более старом Android полнота системных сведений ниже. ApplicationExitInfo не всегда содержит подробную причину/стек нативного сигнала. Сам механизм не вызывает тестовый вылет на рабочем телефоне.

Для включения серверной доставки нужен новый APK 1.0.3 (5): установленный 1.0.2 (4) самостоятельно новый код не получит. Подпись тестовой сборки прежняя; данные сохраняются при обновлении предыдущего тестового APK. Для Play используется прежний ключ владельца.
