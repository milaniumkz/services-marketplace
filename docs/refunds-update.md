# Блоки 6–7: частичные возвраты и остатки

## Реализованный локальный цикл

Пользователь получает собственные подтверждённые платежи через GET `/billing/refundable-payments`: непрозрачный ID, дата, сумма/валюта, тип права и фактический остаток. Курсор и limit применяются в БД до расчёта балансов; суммы возвратов и резервов запрашиваются двумя агрегатами для страницы. Receipt, банковская транзакция и чужие платежи не раскрываются.

POST `/billing/refund-requests` с payment_id и amount_minor создаёт заявку на полный или частичный возврат. Сумма — положительное целое в minor units, не выше доступного остатка. Проверяются владелец, страна, подтверждённый платёж, окружение и исходная денежная сумма. requested/approved/pending/unknown резервируют средства; confirmed учитывается через неизменяемую денежную запись, rejected/canceled/failed освобождают резерв. Idempotency-Key сохраняет результат при потере ответа.

GET `/billing/refund-requests` показывает только собственные заявки. POST `/{id}/cancel` требует владельца, version и requested. Старые обращения по subscription_id без payment_id остаются обращениями для сопоставления: их нельзя отправить на выплату без подтверждённого платежа; отмена и отказ возможны.

Админка `#refunds` открывается из финансового журнала. Доступ billing + MFA и страна сотрудника. Есть список/курсор, детали, сумма, оплата, подтверждённые возвраты, резервы других заявок и доступный остаток. Команды с expected_version и причиной: approve/reject, submit, reconcile. Собственную заявку согласовывает другой сотрудник. Несохранённая причина сохраняется при ошибке; повторная команда блокируется на время запроса.

## Контракт платёжного адаптера

В BillingProvider добавлены необязательные методы, без включённого runtime-адаптера:

- `requestRefund({request_id, transaction_id, user_id, country, amount_minor, currency})` возвращает reference принятого запроса, а не доказательство возврата. request_id — стабильный ключ дедупликации. Адаптер обязан применять его и ограничивать время сетевого вызова.
- `verifyRefund(request_id, accountId)` возвращает проверенное серверное подтверждение: provider, request_id, refund_id, transaction_id, user_id, country, amount_minor, currency, environment и status pending/succeeded/failed. Данные клиента доказательством не являются.

Без метода отправка/сверка возвращает PROVIDER_UNAVAILABLE; состояние не становится успешным. Timeout или некорректный ответ отправки сохраняет unknown и резерв. Повторный submit закрыт; нужна сверка по стабильному request_id. Неопределённая сверка также сохраняет резерв. Нельзя считать timeout отказом и повторно тратить остаток.

Сверка проверяет все поля доказательства, окружение платежа и production-режим. Один refund_id не может подтвердить разные заявки; это защищено блокировкой и уникальным индексом. Несоответствующее подтверждение отклоняется без изменения заявки/баланса. Отказ провайдера завершает заявку failed без денежного события.

## Денежный журнал и доступ

Только succeeded добавляет append-only payment_transaction с operation=refund, отрицательным cash_amount_minor, исходным payment_id, request_id и refund_id. Оригинальная покупка не изменяется. Частичный возврат сохраняет доступ. Полный возврат текущего платежа отзывает соответствующую подписку/grant либо boost; добавляется отдельное нулевое событие access_reversal. Старый полностью возвращённый платёж нельзя использовать для повторной выдачи доступа через restore с новой ревизией.

Подписка хранит current_transaction_id. Возврат старого периода не отзывает более новую оплаченную покупку. Если связь с правом недостаточна, деньги фиксируются правдиво, а применение к доступу помечается requires_review. Результат виден сотруднику. Существующие заказы и поддержка не удаляются возвратом подписки.

Миграция `0010_refund_balances.up.sql` добавляет индексы балансов/идентификаторов и уникальность подтверждения. Для продвижения сохранён тот же порядок блокировок boost → target → capacity → transaction, что и при подтверждении покупки. Все изменения подтверждения и ledger выполняются в транзакции команды; внешний адаптер должен дедуплицировать request_id и после отката БД.

## Проверки и оставшаяся работа

Три новых API-сценария охватывают частичные/полные суммы, остатки, идемпотентность, владение, независимое решение, версии, отсутствие адаптера, unknown/timeout, невалидное доказательство, отказ/отмену/отклонение, повтор refund_id, неизменяемость, восстановление возвращённой покупки, более новый платёж и полный возврат продвижения. Тестовые адаптеры находятся только в проверках.

Банковский адаптер, его реальные операции/подписи/статусы, периодическая автоматическая сверка и проверка нескольких процессов на целевом PostgreSQL ещё требуют подключения и эксплуатационной проверки. Общий reconciliation/adjustment ledger блока 6 не закрыт. Новые клиентские API нужно связать с соответствующими мобильными экранами и принять визуально в блоках 13/15/16/18. Эти изменения не означают, что остались только интеграции. Рабочий сервер не обновлён.

Итог проверки: все workspace-сборки успешны, 102 теста API прошли без ошибок. Браузерный real-HTTP прогон прошёл: согласование, отказ отправки без адаптера, отправка и сверка через изолированный тестовый контракт, отрицательная денежная запись в журнале; экспортированы 72 исходных кадра без ошибок маршрутов. Дополнительный снимок `design/review/admin/refund-confirmed.png` не принят как 1:1. После запрета переноса идентификатора платежа между sandbox/production повторно прошли сборка API и 16 связанных тестов. Реальный провайдер не подключён.
