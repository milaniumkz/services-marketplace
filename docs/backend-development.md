# Backend JOBA: запуск и подключение интеграций

ТЗ: [JOBA v1.1](spec/services-marketplace-spec-v1.ru.md). Исходный набор проверок и ограничения: [статус](backend-status.md).

## Быстрый старт

Node.js 24.19.0 (проверенная версия, `.nvmrc`), npm. Из корня репозитория:

```sh
npm ci
npm run verify
npm run dev:api
```

API запускается на loopback, порт 3000. `/health` сохраняет прежний контракт scaffold. Бизнес-маршруты находятся под `/api/v1`. Полный HTTP-инвентарь: [OpenAPI 3.1](api/openapi.json). Спецификация генерируется `node scripts/generate-openapi.cjs`; некоторые DTO пока разрешают дополнительные поля и требуют дальнейшего уточнения.

Без `DATABASE_URL` используется **PGlite, локальный PostgreSQL в одном процессе**. Данные сохраняются в `.local/joba`. Это не SQLite и не память браузера. PGlite подходит для разработки; production требует серверный PostgreSQL и явный `JOBA_REGION`.

Секреты, файлы пользователей и локальные БД не входят в Git. `.local/` игнорируется. Обычный запуск не создает пользователей, заказов, тарифов, рекламных наград или успешных ID-проверок. Первоначальный каталог содержит только справочные категории/переводы; начальный словарь запрещённых слов пуст.

## Конфигурация сервера

| Переменная | Назначение |
|---|---|
| `API_HOST`, `API_PORT` | Адрес и порт API; по умолчанию loopback:3000 |
| `DATABASE_URL` | Подключение к выбранной региональной PostgreSQL; хранить вне Git |
| `JOBA_REGION` | KZ/RS/RU/BY; обязателен при production |
| `JOBA_DATA_DIR` | Необязательный локальный каталог PGlite |
| `JOBA_UPLOAD_DIR` | Закрытый каталог шифрованных файлов, не публиковать через nginx/static |
| `JOBA_FILE_KEY` | 32 байта в hex, передаются безопасным каналом; обязателен для production-файлов |
| `JOBA_CLAMSCAN_PATH` | Путь к ClamAV с актуальной базой сигнатур |

При разработке ключ файлов создается один раз в закрытом каталоге с правами 0600. Его нельзя терять или заменять без миграции: он нужен для чтения сохранённых файлов и проверки idempotency/cursor HMAC. Ключ нужно сохранять отдельно от базы при переносе и резервировании. В production автоматически создавать новый ключ вместо заданного запрещено.

Применение схемы: `services/api/migrations/0002_runtime.up.sql`. Текущий Store применяет идемпотентную схему при инициализации; до production следует выделить отдельного пользователя миграций и ограничить права runtime-пользователя. `0001_extensions.up.sql` остается исходным отдельным шаблоном PostGIS, автоматический startup его не выполняет.

## Контракт клиента

- `Authorization: Bearer <access_token>`. Токены непрозрачны, на сервере хранятся хеши. Refresh вращается; повтор старого refresh отзывает всю семью.
- Все изменяющие пользовательские/служебные команды требуют `Idempotency-Key` длиной 8–128. Повтор с другим телом возвращает 409. Ключи auth/recovery/webhooks не сохраняют токены в idempotency-таблице.
- Команды с состоянием требуют `expected_version` либо HTTP `If-Match`.
- Ответы: `data` + `meta`, ошибки: `error {code,message,details,request_id,retryable}`. Пароли/подписи не отражаются в ошибках.
- Величины денег — целые minor units. Цена услуги принадлежит сторонам; комиссия с заказа и escrow не реализуются.
- Списки имеют `limit` 1–100 и непрозрачный cursor, связанный с пользователем, маршрутом и фильтрами.
- WebSocket `/api/v1/events/ws`: протоколы `joba.v1` и `auth.<access_token>`. Для native-клиента доступен Authorization header. События содержат ссылки на объекты; детали загружаются с обычной ACL. `resume` с `after_sequence` восстанавливает пропуски. Срок/отзыв сессии проверяются при чтении.
- Staff использует отдельный `/auth/staff-login` и TOTP. Обычный login не создает MFA-сессию. ID-view не наследуется из обычного administrator permission.

## Файлы и документы

`POST /uploads/initiate` → авторизованный binary `PUT /uploads/{id}/content` → `POST /uploads/{id}/finalize`. Проверяются размер, назначение, magic bytes, антивирус. JPEG/PNG декодируются с pixel limit и перекодируются без EXIF/GPS. PDF остается закрытым, пока не зарегистрирован безопасный PDF sanitizer. При отсутствии scanner файл не становится clean.

Файлы хранятся AES-256-GCM в закрытом каталоге. `download` проверяет владельца/участие; для ID нужен отдельный permission, MFA, причина и аудит. `download-url` выдает одноразовую ссылку до 5 минут; при использовании повторно проверяется действующая семья сессии и ACL. Шифрование файлов не заменяет TLS, защищённые диски БД, резервирование и права ОС.

Для проверки исполнителя сначала публикуются правовое основание и country verification policy, пользователь принимает точную версию, затем отправляет clean uploads. Reviewer принимает решение по конкретной ревизии и задаёт срок проверки. Загрузка или локальный PIN не выдают passed.

## Провайдеры

Порты определены в `services/api/src/providers.ts`: BillingProvider, RewardProvider, PushProvider, FileScanner, PdfSanitizer. По умолчанию реестры платежей/рекламы/push пусты. Подключение выполняется доверенным серверным кодом, а не произвольным URL из клиентского запроса.

Платёжный адаптер проверяет подпись/API провайдера, merchant/app/package, среду, SKU, принадлежность аккаунту, валюту, сумму и revision. Backend сохраняет ledger и выдаёт право только по этому подтверждению. Webhook ACK следует за commit. Restore не переносит покупку на другой аккаунт.

Reward-адаптер проверяет SSV/эквивалентную подпись. Сессия сохраняет snapshot политики и окно позднего подтверждения. Выключение rewarded не отменяет обещанную уже начатую сессию. Ban/expiry не закрывают privacy и support.

Push-адаптер подключается позднее с Firebase. Outbox содержит event ID и нейтральное сообщение. Отсутствие провайдера не считается успешной отправкой. Worker учитывает предпочтения и quiet hours, делает bounded retry, затем dead-letter. `sent` означает принятие провайдером, не доставку или чтение клиентом.

## Изолированные проверки

`npm test` запускает доменные/HTTP health проверки с отдельными in-memory PostgreSQL экземплярами. Тестовые provider doubles находятся в тестах; настоящая антивирусная или финансовая интеграция ими не подтверждается.

`npm run seed:local` создает **только изолированные синтетические** аккаунты в `.local/e2e/joba`, секреты — в `.local/e2e/development-accounts.json` (0600). Этот набор не используется обычным API и запрещён в production.

`scripts/verify-postgres.cjs` и `scripts/verify-http.cjs` предназначены исключительно для свежей временной PostgreSQL на 127.0.0.1:5439. Первый отказывается работать в непустой базе пользователей. Они читали созданный для проверки `.local/postgres-test.env`; его значения не нужно публиковать. Контейнер, пароли и набор 5000 заказов не являются application defaults.

Повторная проверка Docker должна использовать новый собственный временный контейнер, не существующую БД пользователя. Проверенный образ: `postgres:16` с digest `sha256:ca0bd484cb98bf4b24eb1010e73fb3fcbd6714d240fbc1a10eea5b7dbecb641d`.

## Docker backend

Из корня: `docker build -f services/api/Dockerfile -t joba-api .`. Node image закреплён digest, runtime работает пользователем node. `.dockerignore` исключает локальные ключи, пользовательские данные, .env и Git.

Для установленного TLS-прокси используйте его системный CA-бандл как временный build secret:

```sh
BUILDX_CONFIG="$PWD/.local/buildx" docker build \
  --secret id=npm-ca,src=/etc/ssl/certs/ca-certificates.crt \
  -f services/api/Dockerfile -t joba-api .
```

NODE_EXTRA_CA_CERTS задаётся только на время npm ci при наличии build secret. Проверки TLS/checksum включены; CA не копируется в runtime image. Сборка и запуск на отдельном временном PostgreSQL проверены через health/bootstrap HTTP. Это не подтверждает legal/provider/production readiness.
