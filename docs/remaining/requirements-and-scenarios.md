# Требования и сквозные сценарии: незакрытая приёмка

Срез `87ec2d8`. Это очередь доказательств по ТЗ. Наличие кандидата теста не означает выполнение требования. Изменения владельца применяются поверх исторического текста ТЗ; SMS, пользовательский email, подписка заказчика и магазинный billing не добавляются вопреки принятой модели.

## Требования

### FR-001

**FR-001 P1.** Заказчик ищет исполнителей по категории, месту, расстоянию, цене и репутации; создает заказ; получает отклики; выбирает исполнителя; общается; фиксирует результат и оставляет оценку.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-002

**FR-002 P1.** Исполнитель создает профиль услуг, задает категории, географию, формат и ориентировочные цены; находит подходящие открытые заказы; откликается; выполняет выбранный заказ; оценивает заказчика.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-003

**FR-003 P1.** Доменная роль не равна оплаченной подписке. Доступ проверяется сервером по аккаунту, роли, стране, состоянию объекта и действующему праву. Изменение интерфейса или подмена role в запросе не дает разрешений.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-004

**FR-004 P1.** Локаль интерфейса выбирается независимо от страны услуги. Страна определяет каталог, правила допуска, правовые версии, платежные SKU и регион данных. Изменение страны не выполняет скрытый перенос персональных данных.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-005

**FR-005 P0.** До запуска утверждаются оператор данных, места первичного сбора и хранения, резервного копирования, перечень получателей и основание трансграничной передачи по каждой стране. Одна глобальная база по умолчанию запрещена как нерассмотренное решение.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-006

**FR-006 P1. Зафиксировано последним уточнением пользователя.** Регистрация: номер телефона и самостоятельно установленный пароль. Вход на новом устройстве: тот же номер и пароль. SMS-коды, телефонные одноразовые коды и SMS-интеграции полностью исключены, в том числе из восстановления. Телефон является неподтвержденным идентификатором входа, а не доказательством владения номером или личности.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-007

**FR-007 P1.** Backend применяет rate limit и backoff по аккаунту, IP и устройству, защищаясь от brute force, credential stuffing и блокировки жертвы чужими попытками. Ошибка входа не раскрывает, существует ли номер. Access token предложено на 10 минут; refresh на 30 дней с ротацией, хранением хеша и отзывом token family при replay. Сессия сохраняется в защищенном хранилище устройства.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-008

**FR-008 P1.** Сохраненная сессия обязательно защищена локальной разблокировкой при открытии приложения: пользователь настраивает PIN и/или доступную биометрию. Если настройка отклонена или безопасный механизм недоступен, требуется полный вход номером и паролем. Поддерживаются Face ID/Touch ID на поддерживаемом iPhone, системный BiometricPrompt и допустимый класс биометрии на Android. Не называть Android-биометрию Face ID. Разблокировка открывает сохраненную сессию; она не создает новую серверную сессию и не заменяет проверку личности.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-009

**FR-009 P1. Обязательная проверка исполнителя.** До допуска к исполнительским функциям пользователь загружает допустимый для страны документ: ID-карту либо паспорт. Набор типов, необходимые стороны/страницы и правовое основание утверждаются по стране; не собирать все страницы паспорта по умолчанию. Одна загрузка не означает verified: назначенный verification reviewer проверяет материал и принимает документированное решение. Для роли заказчика такая проверка не обязательна. Face ID/PIN не заменяют этот процесс.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-010

### FR-011

**FR-011 P1.** Общий аккаунт содержит display name, аватар, языки общения, страну, статус и минимальную контактную информацию. Публичный профиль заказчика показывает имя, аватар, дату регистрации, количество завершенных заказов и подтвержденные взаимные отзывы. Телефон, платежные данные и документы скрыты; пользовательского email нет.

### FR-040

**FR-040 P1. Портфолио исполнителя. Добавлено в v1.1.** В профиле исполнителя размещаются проекты с фотографиями работ, названием, описанием, категорией услуги и необязательной связью с выполненным заказом. Владелец создает/редактирует/удаляет свои проекты, меняет порядок и обложку. Предлагаемые лимиты: до 20 проектов, до 10 фото в проекте, до 5 MB на исходник; название 5–120 символов, описание до 3 000. Эти лимиты отдельны от галереи профиля и утверждаются до реализации. Видео в P1 не входит.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-012

**FR-012 P1.** Категории имеют стабильный ID, дерево с ограниченной глубиной, страну доступности, переводы, иконку из разрешенного набора и набор дополнительных полей заказа. Удаление используемой категории заменяется архивированием; существующие заказы сохраняют снимок названия.

### FR-044

**FR-044 P1. Топ-100 и реакции. Добавлено в v1.1.** Два отдельных типа выдачи: открытые заказы заказчиков и карточки услуг исполнителей. Карточка услуги — существующий профиль × категория с устойчивым catalog_card_id, его описанием/ценой и ссылкой на профиль, а не новая вакансия или самостоятельный магазин товаров. Топ имеет фильтры country/city/category/target_type и показывает до 100 реально допустимых объектов; при меньшем количестве не заполняется вымышленными. Действуют entitlement, страна, видимость, блокировки и executor_verified владельца карточки услуги.

### FR-045

**FR-045 P1. Платное и административное продвижение.** Пользователь выбирает собственный допустимый заказ либо карточку услуги, место показа, страну/город/категорию и разовый срок: неделя, месяц или год. Пример «неделя за 200 ₸» не утвержденная цена. Неделя предложена как 7 суток, месяц/год — календарные периоды с серверной UTC-границей и явным отображением IANA zone; точная модель фиксируется offer snapshot. Для заказа boost end не может быть позже известного expires_at: несовместимые сроки, включая год для краткосрочного заказа, не предлагаются; заказ автоматически не продлевается. Preview объясняет прекращение показа при раннем выборе исполнителя/закрытии заказа и применимую refund policy. Автопродления по умолчанию нет. Продвижение не добавляет likes/звезды и не переписывает organic rank. Платные и административно продвинутые карточки находятся в отдельно обозначенных местах «Продвигается»; алгоритм органического Топа остается независимым.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.

### FR-014

**FR-014 P1.** Сервер принимает только перечисленные переходы. Каждый переход проверяет роль, version, текущее состояние и отсутствие запрещающего moderation hold. Ограничение страны на новый бизнес не запрещает безопасно завершить уже выбранный заказ. Иные переходы возвращают 409 STATE_CONFLICT с актуальной версией.

### FR-015A

**FR-015A P1.** Из карточки исполнителя заказчик выбирает «Предложить заказ»: выбирает свой open-заказ либо создает новый, затем отправляет приглашение. Invite имеет pending / accepted / declined / expired / revoked, срок 72 часа и уникальную активную пару order + contractor. Принятие приглашения открывает заполнение обычного отклика; assignment и свободный чат сами собой не создаются. До отклика исполнитель может отказать без контакта. Лимит предложено 10 приглашений в сутки, с pair block и действующими правами обеих сторон.

Статус реестра: `pending`. ☐ Связать с экраном/контролами, API и негативными проверками; ☐ закрыть фактические пробелы; ☐ записать команду, commit и результат. Не отмечать passed по одной сборке.
