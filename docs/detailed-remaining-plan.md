# JOBA — подробный план завершения пользовательской и административной частей

Срез: **19 октября 2026, исходники `87ec2d8`, ветка `feat/joba-implementation`**. План основан на ТЗ v1.1, реестре макетов, OpenAPI, текущих исходниках и накопленных результатах проверок. Это аудит оставшейся работы и доказательств, а не заявление о полном ручном тестировании всех функций в этой итерации. Новые продуктовые проверки в рамках составления плана не запускались.

## 1. Что осталось в целом

В реестре **191 кадр: 115 mobile, 67 admin, 9 public**. Из них 187 исходных и 4 добавленные коммерческие страницы. Все имеют незакрытую визуальную приёмку. **2 989 элементов** перечислены индивидуально; их связи с API/локальным действием и доказательствами ещё не заполнены. Это не 2 989 доказанных неисправностей. Дополнительные рабочие экраны финансов, возвратов и ролей требуют отдельной приёмки сверх исходного набора.

Последнее зафиксированное полное прохождение API — 126 тестов, после последнего ограничения поиска прошли 11 связанных тестов. Браузерный сценарий проверял реальный изолированный HTTP API и 72 исходных кадра, дополнительно — создание роли, назначение и вход ограниченного сотрудника. Эти результаты не доказывают соответствие всех экранов или готовность production. В рамках этого аудита сервер не опрашивался: последняя ранее зафиксированная версия production — `75cedf3`, свежая ветка туда не развёрнута.

Подтверждённые незавершённые направления:

- Мобильные заявки на возврат и история подключены в следующей итерации: [результат](mobile-refunds-update.md). Их визуальная и расширенная сквозная приёмка остаётся открытой.
- Оставшиеся категории минимизации/удаления, история проверок документов и согласий, финансовые/аудитные записи, неоднозначные старые данные; корректное окончательное состояние задания.
- Индивидуальное соответствие кнопок старых административных редакторов точным правам динамических ролей; первичное подключение сотрудников остаётся защищённой внеинтерфейсной процедурой.
- Полная визуальная и функциональная приёмка каждого состояния; часть прежних сценариев могла быть только выбором записи/просмотром версии — каждый нужно перепроверить.
- Эксплуатационные проверки PostgreSQL несколькими процессами, нагрузка, реальные устройства, сборки и доступность.
- Внешние подключения и развёртывание — отдельная очередь; доступную локальную работу ими не блокировать.

## 3. Правила выполнения маленького блока

Каждый блок ниже разбивается на **одну страницу → одно состояние → одно действие/поле**. У действия отдельные отметки: реализация найдена, результат проверен, ошибки/права проверены, визуальная приёмка выполнена. Не переписывать уже работающую функцию без выявленного дефекта.

Для каждого поля: исходное значение из API, допустимые значения/границы, обязательность, ввод/очистка/выбор, сообщение рядом с полем, сохранение после ошибки, результат после повторного открытия. Для каждой кнопки: точный обработчик, правильная запись и регион, права, busy/disabled, повтор/потеря ответа, результат и навигация. Для каждой таблицы/списка: реальные данные, фильтры, сортировка, cursor-пагинация, пустой результат, сохранение контекста после открытия карточки.

Для каждой страницы: загрузка, применимое empty, ошибка с повтором, offline, истечение сессии, запрет доступа, изменение данных другим клиентом, длинный текст, клавиатура, увеличенный шрифт и screen reader. Не добавлять бессмысленное empty для страницы без списка; неприменимость фиксировать.

Визуальный шаг: исходный viewport → эталон рядом с текущим кадром → геометрия/шрифты/цвета/иконки/изображения → исправление → повторный снимок. Реальные имена и суммы не копировать из демо; системные области и утверждённые изменения владельца описывать как разрешённые различия. Автоматическая доля отличающихся пикселей не закрывает приёмку.

Карточка дефекта: ID кадра/контрола, шаги, ожидаемое/фактическое, источник требования, приоритет, исправляющий commit, проверка, снимок. Приоритет P0 — доступ/утечка/деньги/потеря данных; P1 — обязательный сценарий/неработающее действие; P2 — визуальное расхождение/доступность/удобство. Каждый блок закрывается только при отсутствии его открытых обязательных дефектов.

- ☐ Android/web релизы на финальном commit; iOS в поддерживаемой среде; реальные PIN/biometry/share/files/permissions/background/reconnect/deep links.
- ☐ Screen reader/keyboard/focus, крупный текст, узкий экран, длинные переводы и все поддерживаемые языки; никаких потерянных кнопок под клавиатурой.

Результат: протокол замеров с данными/окружением, закрытые узкие места, подтверждённые платформы. «Моментально при любой сети» не является проверяемой гарантией.

## 20. Очередность выполнения и финальная передача

1. Реестр/актуальные требования → P0-дефекты доступа/денег/удаления → оставшиеся самостоятельные функции (возвраты UI, retention, точные состояния прав).
2. Пользовательская часть: блок 4 → 5 → 6 → 7 → 8 → 9 → 10. В каждом экране сразу исправлять визуальные расхождения и проверять действия, не откладывать все проверки на конец.
3. Админка: 11 → 12 → 13 → 14 → 15 → 16; публичная часть 17. Общие API/компоненты исправлять согласованно с обеими UI-частями.
4. Сквозная регрессия/скорость/доступность 18–19; повторные снимки после общих изменений; каждое требование и контрол имеют доказательство или явно открытый пункт.
5. Зафиксировать проверенный commit, команды сборки/запуска/миграций/отката, матрицу приёмки, известные ограничения и эксплуатационные инструкции. Не использовать процент готовности без согласованного знаменателя и проверки каждого пункта.

Для каждого маленького блока результат: исправление при необходимости → целевая проверка → снимок/сравнение → запись в реестр → Git. Более широкую регрессию запускать при затронутых общих компонентах, а не после каждой правки текста.

## 21. Отложенные внешние подключения и сервер

Отдельно от самостоятельной разработки: банк/платёжный провайдер и реальные callbacks/refunds/reconciliation; рекламная сеть/SSV; Firebase/native push; карта/геолокационные сервисы при необходимости; серверы/постоянные хранилища/очереди/секреты; DNS/HTTPS и деплой выбранного commit через GitHub с миграциями и откатом; backup/restore RPO≤15 минут/RTO≤4 часа; реальные устройства и проверка банка.

Расположение и доступ к данным документов согласовать с фактической инфраструктурой и требованиями страны. Не включать видимость успешной интеграции без неё. Все страны остаются активными согласно решению владельца; недоступность конкретного сервиса отображается адресно.

Статус «остались только интеграции» допустим после закрытия всех самостоятельных функций и их приёмки выше. Сейчас оснований для него нет.
