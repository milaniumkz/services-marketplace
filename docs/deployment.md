## Состав

- `/` — release web-сборка Flutter, API текущего региона KZ на том же HTTPS-origin.
- `/admin/` — служебная панель с MFA; `/site/` — публичные информационные страницы.
- `/api/v1/` и `/health` — API за Caddy. WebSocket использует тот же reverse proxy. API доверяет ровно одному Caddy-hop (`JOBA_TRUST_PROXY=1`); контейнер API не публикуется напрямую, входящие forwarded headers очищает Caddy.
- Отдельный PostgreSQL 16, постоянные Docker volumes БД, зашифрованных файлов и сертификатов. БД и порт API наружу не публикуются.
- Caddy получает и продлевает публичный сертификат. Домен должен указывать на сервер; 80/443 должны принимать входящие соединения. Самоподписанный сертификат и отключение TLS-проверки не используются.
- AV-сигнатуры обновляет отдельный freshclam. До доступности настоящих сигнатур загрузки не получают фиктивный `clean`.

## GitHub Actions

[Workflow](../.github/workflows/deploy.yml) запускается push в `deploy/joba` или вручную, когда workflow зарегистрирован GitHub. Публикуется точный commit, без merge в main. Одновременно выполняется только одно развёртывание.

1. `inspect` проверяет DNS, TCP/SSH banner и сохраняет **публичные** host keys как артефакт. Это не вход на сервер и не proof of deployment. Сверьте fingerprint с панелью хостинга перед закреплением.
2. `build` проверяет код и собирает Flutter web / admin / site. Flutter закреплён на проверенном commit; Actions закреплены SHA. Архив содержит manifest commit/checksums, без локальных данных, паролей или пользователей.
3. `deploy` использует строгую проверку SSH host key и защищённые Actions Secrets. Сервер получает исходники через Git по точному commit; фронтенд проверяется по manifest. Скрипт готовит Docker на Ubuntu/Debian, сохраняет серверные ключи вне Git, резервирует предыдущие данные и запускает compose. Успех фиксируется только после проверенных HTTPS-запросов.

Необходимые [Actions Secrets](https://github.com/milaniumkz/services-marketplace/settings/secrets/actions):

- `JOBA_SSH_PRIVATE_KEY` **или** `JOBA_SSH_PASSWORD` — доступ root для первоначальной настройки. Пароль нельзя коммитить или передавать через публичные workflow inputs.

ED25519 host key закреплён по fingerprint, полученному первым read-only сканированием из GitHub runner: `SHA256:Bt3HkaktjLmWe4tB1pOK9b8gOnHuxp+tvp1hhEDtxp8`. Перед каждым входом скан сверяется с этим pin, затем SSH работает с StrictHostKeyChecking=yes. Подмена или изменение ключа блокирует вход. Значение ключа публичное; отдельный секрет для него не нужен.

В текущем подключении GitHub отклонил чтение ключа шифрования Actions Secrets: HTTP 403 `Resource not accessible by integration`. Secrets остаются предпочтительным вариантом для будущих запусков. Для первого разрешённого запуска есть одноразовый OAEP handoff: runner создаёт временную RSA-3072 пару, публикует только public key/nonce/commit/run, читает привязанный к этой задаче шифрованный envelope из отдельной временной ветки, маскирует пароль и удаляет private key. Агент сверяет источник challenge и шифрует уже предоставленный пароль. В исходниках и основных ветках plaintext отсутствует; временная ветка удаляется после получения. Неправильный nonce/run/commit отклоняется; ожидание ограничено 10 минутами. Реальная доставка проверена в разрешённых запусках GitHub; временные ветки удалены, приватные ключи runner уничтожаются после получения. Открытый пароль не сохранялся в Git.

Из текущей облачной среды две SSH-попытки на порт 22 завершились `Connection refused` до авторизации. HTTP/HTTPS-проверки блокировались политикой прокси; IP и домен добавлены в черновик разрешений среды, который нужно сохранить и опубликовать. Это не доказывает неисправность самого сервера. Read-only проверка из GitHub runner прошла: TCP/SSH доступен, host keys получены. Затем вход и запуск подтверждены успешным workflow развёртывания и независимой проверкой публичного HTTPS.

## Серверные данные и повторное развёртывание

`/etc/joba/production.env` создаётся с правами 0600 и содержит постоянный ключ файлов и пароль PostgreSQL. При обновлении их нельзя регенерировать. Исходники находятся в `/opt/joba/releases/<commit>/source`; ссылка `/opt/joba/current` меняется после успешной HTTPS-проверки. Пользовательские изменения release checkout блокируют перезапись.

Перед повторным запуском существующей установки сохраняются SQL dump, зашифрованные файлы и ключи в закрытом `/var/backups/joba/<UTC>/`. Offsite backup и проверка восстановления остаются отдельной эксплуатационной задачей. Автоматического отката БД нет: после неудачной миграции сначала проверяются фактические контейнеры и схема, затем принимается решение о восстановлении.

Служебные аккаунты создаются только существующим offline bootstrap CLI; тестовые пароли/пользователи не публикуются. Правовые документы, тарифы и доступность стран требуют действительной административной настройки. Платежи, рекламная сеть и Firebase остаются отключёнными до предоставления интеграций. Наличие развёртывания не означает выполнение всего ТЗ или совпадение макетов 1:1.


Первичная публикация документов KZ разрешена владельцем 15.10.2026 с временно пустыми реквизитами. Тексты: `docs/legal/kz/terms.ru.txt` и `privacy.ru.txt`. Скрипт `publish-initial-kz-legal.cjs` запускается после резервного копирования и обновления API; он публикует только отсутствующие семейства документов, фиксирует основание в audit и не изменяет существующие версии. Это поручение владельца, а не фиктивное согласование вторым сотрудником и не заключение о юридической готовности. После первой публикации редактировать через админку → «Правовые документы» → «Редактировать новой версией», заполнить реквизиты в тексте и направить новый черновик на обычную публикацию другим уполномоченным сотрудником. Подтвердить локализацию базы, файлов и резервных копий в Казахстане до коммерческого запуска.

Веб-сборка отключает устаревший Flutter service worker. Bootstrap автоматически снимает регистрацию только корневого `flutter_service_worker.js` и один раз перезагружает управляемую им вкладку. Удаляются только три служебных Flutter-кэша; сессия, настройки и другие service workers сохраняются. Регрессия миграции: `node scripts/verify-web-worker-upgrade.cjs`.
