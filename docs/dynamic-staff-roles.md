# Динамические роли админки

В разделе «Роли и сотрудники» владелец создаёт именованные роли, отмечает блоки и отдельные функции, редактирует/архивирует роли и назначает сотруднику несколько ролей. Выбор блока включает его функции, отдельные функции можно отключить. Просмотр документов и служебных файлов выдаётся отдельно. В поддержке отдельно разрешаются назначение, закрытие, ожидание ответа и повторное открытие. Для работы через экран нужно также выбрать необходимые операции просмотра списка/записи.

Роли и назначения действуют в одной стране. Назначение управляемых ролей заменяет прежние прямые права сотрудника; пустой набор отзывает доступ к функциям. Архивирование или изменение роли применяется при следующем запросе уже открытой сессии. Действующий сотрудник входит через служебный пароль и MFA. Обычный пользовательский аккаунт этим экраном в сотрудника не превращается.

Проверки API разрешают только выбранные операции из явного каталога. Неизвестные операции запрещены; нельзя назначить wildcard, управление ролями или владельца обычной ролью. Чувствительные документы требуют дополнительного права. Глобальный поиск ограничен явно разрешёнными разделами; право на файлы не открывает поиск по другим блокам. Ранее выданная ссылка на файл также заново проверяет текущую роль. Право загрузки позволяет просматривать статус собственных файлов, не чужих. Проверка выполняется и до возврата сохранённого идемпотентного ответа. Мутации сотрудников и смена прав используют согласованные блокировки страны; вход с MFA также защищён от перезаписи одновременного назначения. Независимое согласование, версии, причины, MFA и существующие ограничения по стране продолжают действовать.

Изменения ролей и назначений записываются в неизменяемый аудит с составом прав до/после. Понижение владельца через назначения запрещено. Новые роли не дают статус владельца. Существующие сотрудники с прямыми правами продолжают работать до явного перевода в управляемые роли.

## Первоначальное подключение

Первый владелец задаётся защищённой офлайн-процедурой `scripts/bootstrap-staff.cjs` с правом `platform_owner`. Обычный `administrator` не считается владельцем и не может присвоить себе управление доступом. Конфигурация владельца содержит отдельный staff-идентификатор, регион, имя, пароль и основание; файл имеет режим 0600, пароль и секрет MFA не передаются через аргументы командной строки и не попадают в Git. Используются существующие переменные JOBA_STAFF_BOOTSTRAP, JOBA_STAFF_CONFIG_PATH и JOBA_STAFF_ENROLLMENT_PATH.

Сотрудники также подключаются отдельной служебной процедурой с MFA. После подключения владелец назначает им управляемые роли в админке. Создание пароля/MFA через веб и самостоятельная регистрация сотрудника этим изменением не добавлены. На сервере владелец ещё не назначен этим изменением; развёртывание не выполнялось.

## API и сопровождение

GET /admin/access/me — фактический доступ текущей сессии; остальные /admin/access/* доступны только владельцу: каталог, роли, создание/редактирование/архив, список сотрудников и назначение ролей. В OpenAPI добавлено 8 операций. Каталог конкретных разрешаемых функций хранится в services/api/src/staff-operation-catalog.ts; после изменения API его воспроизводят `node scripts/generate-openapi.cjs` и `node scripts/generate-staff-catalog.cjs`. Новая операция не разрешается автоматически старой роли.

Открыто: проверка нескольких реальных процессов PostgreSQL, расширенная визуальная приёмка, полное отображение каждого запрещённого действия во всех старых редакторах. API запрещает такое действие независимо от наличия старой кнопки. Для управляемого сотрудника скрыты чужие пункты меню, экраны просмотра блокируют изменение, основные действия поддержки/дел проверяют отдельные права. Механизм не подтверждает готовность всего приложения или совпадение всех экранов 1:1.

Проверки: сборка всех workspace, 126 успешных API-тестов без ошибок/пропусков. Браузерный сценарий проверил создание/назначение роли, отдельный вход сотрудника с MFA, разрешённую поддержку, скрытие чужих разделов и запрет прямого перехода; сохранены 72 исходных кадра без визуального принятия. После дополнительного ограничения глобального поиска повторены сборка API и 11 связанных тестов — все успешны. Сервер не обновлялся.
